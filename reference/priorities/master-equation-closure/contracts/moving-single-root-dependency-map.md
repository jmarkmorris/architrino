## Parsing, selection, and impact

Pinned dependencies in the repository package and lockfile are `jsonld@9.0.0`, `n3@2.7.12`, and `@comunica/query-sparql-rdfjs@5.3.0`. Digital Bazaar's JSON-LD implementation expands the versioned local context and emits N-Quads with safe mode enabled. N3 parses those quads into an RDF/JS store. Comunica executes one fixed local SPARQL property-path query on a separate derived impact store. No remote context loader, remote query source, user-supplied query, `SERVICE`, update operation, persistent database, or command dispatch from graph data is enabled.

The project-specific layer validates the exact supported fields, local context, object kinds, unique object/relationship identities and aliases, endpoint revisions, selected relationship type constraints, source paths, and selected-byte digests. It preserves CRLF and final unterminated lines for the current fixed line selectors and requires unique literal selectors. A changed line placement can require rebinding even when mathematics is unchanged; this trial deliberately retains the reviewed selectors. JSON member-name duplicates are not separately detected by the JavaScript JSON parser. Exact input/map bytes are recorded for review, and neither parsed nor RDF equivalence grants acceptance.

Relations distinguish mathematical, domain, implementation, comparison, and provenance meaning through their explicit role and explanation. The code validates shape and the declared endpoint constraints; it cannot judge mathematical implication or completeness. In particular, a refreshed but scientifically unsupported dependency can pass structure and still remain review-required. That negative control is intentional evidence of the human review boundary.

The derived impact view follows all declared relationship kinds except `checks` in the dependency direction. It is not a proof graph. Changed relationships seed the affected source endpoint; deleted check coverage seeds the previously covered object. The report takes the union of transitive dependents from both snapshots, then selects check obligations using both old and current coverage. Deleting a dependency or its coverage therefore cannot erase the old review obligation. Added, removed, and changed relationship identities are separately reported. Any changed bound source file conservatively selects both declared check obligations, including an edit outside selected blocks.

## Execution and publication paths

Run the bounded trial with:

```bash
node scripts/equation-mapping/check-moving-single-root-map.mjs
```

It first runs independently specified SHA, selector, hand-graph, removed-dependency, removed-coverage, stale-source, and displayed-result controls. Only then does it read the real baseline and candidate. After successful graph validation it executes the unchanged moving-single-root numerical verifier, compares one uniquely selected displayed maximum against its exact stdout, and runs the existing scientific test. These executions are unconditional within a structurally valid trial, even when the declared impact-selected set is empty; selected coverage and actually executed coverage are separate report fields. If an earlier step fails, later work is not implied to have run.

The report is written to ignored `.local-data/option-b-trial/report.json`, accompanied by exact stdout/stderr for external checks. It records baseline and candidate identities, source and instrument/package digests, runtime, execution outcomes, displayed-value tolerance, and review disposition. The runner checks input-byte stability across successful execution. Each invocation removes its previous report before work begins; an unavailable dependency, missing baseline, stale binding, failed check, or unstable input is an error, not a successful skip. Errors return exit 1; a successful bounded run returns exit 0 with status `pass` or `review-required`. Neither status is an approval.

The local [publication receipt runner](../../../../scripts/pr-validation-receipt.mjs) invokes B after its unchanged four command groups. It records B's explicit outcome, report path and available report digest in a separate `reportOnly` receipt field. A B launch or check error does not fail A's required commands; the log labels that error. An A failure still aborts required validation and can prevent B from being reached. The receipt's existing state comparison remains authoritative for A; the B report digest identifies an execution record and is not a new acceptance condition or archival guarantee.

The same runner additionally executes the [finite-ledger chain](finite-ledger-dependency-map.md), with its accepted baseline explicitly absent. It emits `review-manifest.json` identifying both maps and the scoped source, instrument, test, contract, workflow and package bytes. The manifest is not an approval receipt.

The separate [GitHub workflow](../../../../.github/workflows/option-b-trial.yml) runs on every pull request without a path filter, and on manual dispatch. It checks out full history, selects Node 22, installs the lockfile, runs the controls/entrypoint tests, and runs the candidate trial. Its job is named `B two bounded chains (report-only)` and has `continue-on-error: true`; failed steps remain visible. The always-run summary labels missing/failed execution as `error` and exports `trial-status`. The artifact `option-b-two-chains-<run-id>-<attempt>` retains the B report and outputs for 14 days. A green overall report-only workflow is not evidence that B passed: inspect its explicit status, steps, summary, and artifact. Existing A workflows and Pages remain separate owners.

Keep the bounded parallel role until its actual PR reports have been reviewed for correct detection, explicit failure reporting, useful review output, and acceptable maintenance cost.
