## P-R1: replay validity and selected-record identity are different

The map correctly chooses driver-call legs rather than producer-only replay: the requested end changes final-step clamping and therefore controller state. Keep that choice. Replay must issue genuine evidence and continuation from the actual driver, and must compare every claimed step/leg/final state before returning anything. A disk digest detects corruption relative to its stored value; it does not authenticate the original run.

The binding table nevertheless states that a changed control changes the step sequence or outcome. That is false in general. The separately authored [control probe](../evidence/matched-pair-review-stage3-replay-control-probe.cpp) compiles against the accepted live library and records a known static grouped acceleration enclosure before its target. It changes increment budgets from `0.001` to `0.01`: both genuine runs complete with identical times, counts and full publication chains, while their issued continuations bind different budget controls. No persistence runtime exists yet, so this demonstrates an inadequacy of the proposed detection argument, not a restore implementation defect.

Changing a nonbinding budget in a record and recomputing its digest can consequently leave the claimed step log, outcome and ledger unchanged. Bare replay then constructs valid evidence under the changed controls; it cannot establish that this is the selected original record or original control identity. The same distinction applies to a changed origin or scalar whenever a self-consistent different run is supplied. Mathematical validity under the actual replay inputs is preserved; original identity is a separate claim.

Correct the map and choose an explicit API boundary. Restoration claimed to preserve a selected record must compare against an expected complete record identity or expected controls supplied separately by the caller, not reread as its own authority from the same record. An expected content identity selects exact bytes; it is not an authentication claim. A bare record replay, if retained, must explicitly return only revalidated current-record state and its actual identity, with no claim to preserve the previously selected run. Tests should distinguish raw-digest corruption, recomputed-digest changes to a selected record, and a genuinely self-consistent new record. Do not assert that every changed control must change generated histories or that all alterations can be rejected without an external expectation.

Correct two related statements: per-leg accepted-step limits are recorded operational inputs, not currently bound continuation controls; and replay reruns the steps but equal wall/CPU cost is unmeasured. When appending a plain returned certificate, verify its controls/population/final ledger against its sealed continuation/evidence before treating it as an accepted boundary; mutable certificate fields alone do not establish producer issuance. A mismatched record may be retained as data, but restore must return no usable state on a failed expected identity or replay comparison.

Return this narrow design correction while increment 3 runs.
