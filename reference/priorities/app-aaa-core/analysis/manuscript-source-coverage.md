## Source tensions and editorial treatment

1. **Design versus local execution.** Architecture service verbs span storage, indexing, resource dispatch and remote publication; accepted modules and the client establish bounded in-process conformance. §§1.2,4.1,5.3,7.3 distinguish the scopes; there is no inferred deployed catalog or network transport.
2. **Older remaining-work text.** Path, codec and stream closing sections retain CORE-005/008 as open, while their later accepted owners and work log record local closure. Coverage preserves both records and uses the later explicit contract status for the bounded client/query exposition; no original status is rewritten and no production completion follows.
3. **Authored setup versus continuation.** Architecture's setup flow admits a role for authored past paths, while v0 prescribed history cannot permit continuation. §2.2 separates possible EOM setup admission from accepted continuation and makes no conversion rule or authority upgrade.
4. **Potential ownership history.** Older codec log prose calls the fixture application-owned; the later Core classification and Potential API name it Core-owned. §§1.2,3.1,6.1 follow the explicit recorded consolidation, retaining earlier ownership as provenance, without renaming any version token or external application.
5. **Finite stream versus future live system.** The broker validates predeclared source-manifest chunk identities and retains the whole finite stream; real-time data-plane diagrams describe a broader objective. §4.1 names this gap rather than claiming unbounded append, production retention or an implemented EOM adapter.
6. **Atomic samples versus provisional products.** An atomic Potential request requires complete finite unique rows; a progressive product may expose missing tiles provisionally. §6.3 keeps these boundaries separate. No absent contribution becomes a numeric zero, and incomplete maps cannot seal.
7. **Static observable versus live harness.** The product registry contains one prescribed synthetic observable, while live fixture events mimic EOM-accepted chunks with synthetic authority and placeholder hashes. §6.3 does not invent a shared physical kernel or scientific acceptance across these distinct examples.
8. **Profile versus capability declarations.** Profile requirements, maximum provider capability and selected consumer permission are separate checks. In particular a fixture codec advertising two profiles does not raise display data to its maximum analysis authority; canonical whole-record support is not silently expanded to every profile-level access pattern. No unseen validator resolution is inferred.
9. **Time and identity meanings.** Source accepted-through, delivered, acknowledged, Core consumed-through and map completed-through are different values. Broker and map lag definitions are preserved separately. Source/manifest placeholders, local canonical hashes and consumer-specific receipt hashes serve different roles; an expected fixture digest is not a freshly measured replay result.
10. **Dated hardware versus current decision.** Vendor snapshots and engineering proposals remain supporting history. No current offer, price, performance advantage, vendor ranking or purchase is endorsed by the manuscript.
