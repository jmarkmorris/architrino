## Semantic assessment against the actual obligations

The [EOM contract](../../app-solver/contracts/evolution-contract-v1.md#accepted-step-state-machine) requires immutable input histories, complete root certification before acceleration, rejection before publication when certification fails, and atomic continuation records. Its restart gate requires equivalence under declared policy. The current implementation changes are assessed against those obligations as follows.

1. **Adaptive restart memory and counters.** The current code restores growth-headroom state, accepted/rejected counters, cooldown and fallback state from the request. It checks resource bounds before unsigned subtraction or addition. The loop counts new diagnostic steps relative to the restored accepted count, while total attempts and emitted step indices retain the earlier count. Cancellation is checked at a resumable accepted boundary. These are consistent with continuation from an accepted checkpoint rather than a fresh run. Existing tests cover three adaptive checkpoint cuts, counter overflow, incompatible memory modes, pre-step resource halt, capped counts, and growth-memory resets. Direct/resumed agreement is a replay property; it is not an independent numerical oracle.
2. **Joint-history publication.** Added fingerprints cover the joint representation. The atomicity check compares path identity, symbol registry, all existing segment coefficients and remainder radii, and the published terminal time. The rejected path publishes the input joint histories. This strengthens the structural publication condition. It does not derive the enclosure mathematics or certify a new joint-history scientific campaign.
3. **Sharp acceleration refinement.** The current path allows the same two bounded root-tolerance refinements for sharp-only requests that previously ran only under the finite-width-fallback policy. It installs a refined root only after complete certification, a root-free complement, and no memory-boundary contact. The acceleration request points to the existing root-vector element, whose replacement does not resize the vector; re-evaluation therefore consumes that refined record. Finite-width fallback remains conditional on the explicit fallback policy. A distinct acceleration-enclosure failure is returned when root completeness is established but the sharp width remains uncertified. The change can alter whether a sharp request succeeds, so it is substantive and cannot be described as a mechanical hash repair.
4. **Diagnostic compaction.** The code releases `root_free_cells` from completed diagnostic snapshots while retaining the latest accepted warm-start snapshot until the next accepted step. Final return releases all such cached cells. It does not erase roots, accepted histories, acceleration vectors or the recorded root-free-complement status. This review establishes that local field-level effect by reading the implementation; it does not claim full serialized-proof reconstruction for arbitrary consumers after compaction. Any consumer that requires the individual discarded complement cells needs its own evidence contract assessment.

The fresh unchanged Python regression suite passes 43 tests. Among them, static and super-field inertial histories and a coupled binary step are compared with the separately authored Python `certified_evolution` reference, using its own certified-history representation. The suite also includes exact/rational controls and event-oracle comparisons. Those independent checks support their enumerated cases; the restart comparisons and fixture self-checks have narrower purposes. No subject or reference was modified in this review. Agreement on the suite does not prove every sharp-only request or every diagnostic consumer correct.

The build-specific inference is narrower and stronger than a claim about all evolution: `eom_f5_prehistory_inspector.cpp` imports the History API and implements data parsing, history construction and endpoint inspection; it supplies no coupled evolution request. The circular adapter imports History, Decimal and ExactPairBatch and calls `certify_exact_pair`, without invoking coupled evolution. Both build procedures invoke only `--help` after linking. The reviewed CoupledEvolution changes therefore do not enter their declared build-only execution. This scope is why its current digest can be accepted for a new build source census without granting new evolution authority. An actual call path from either reviewed adapter into coupled evolution, an altered adapter digest, or a newly admitted data/evolution invocation would overturn that inference.

The enclosed-root helper's imported `runWatched` and `scopedPath` implementations are unchanged in the exact old-to-current diff. Their use by these builders does not call the helper's FROZEN input loader. The helper remains unacceptable as an end-to-end F5 input route because its current logical configuration path supplies different bytes from its old expected hash, as reproduced by two preparation tests. Accepting its imported build utilities must not be reported as repairing that loader.

## What the independent review permits and what remains blocked

The minimal builder-only update is three pins in `prepare-f5-prehistory-handoff-build.mjs` (CoupledEvolution, enclosed-root helper and CMake) and one CMake pin in `prepare-subfield-circular-root.mjs`. Because the latter file is itself pinned by the former, changing it also requires binding its newly reviewed resulting bytes in the F5 builder. That fifth transitive edge is a consequence of the scoped edit, not an additional currently mismatching dependency. The integrating task must inventory other consumers before making those edits and test the resulting composition. No such pin was changed here.

**A builder-only pin update cannot complete the F5 handoff.** Both `prepare-f5-prehistory-handoff.py` and the separately authored `verify-f5-prehistory-handoff.py` contain the original CoupledEvolution digest in `SOURCE_OWNERS`. The producer's `check_build` compares the build receipt's sourceOwners to that map, and the verifier's `analyze_data` requires the same original map. Both also authenticate those source bytes at their declared paths. A new builder receipt carrying the current digest is therefore deliberately incompatible with those old contracts. Simultaneously advancing the subject and independent reference would erase this distinction. The needed implementation is an explicit current input/build transport that preserves original handoff and verifier bytes, identifies which unchanged numerical predicates establish the new data result, and carries the actual current source/build bindings separately. This review does not supply that interface or manufacture an accepted handoff.

**A current circular build does not authorize a ladder rung.** `run-subfield-circular-root-rung.mjs` requires a specific recorded build receipt, an accepted independent resource plan, a complete accepted pilot admission, closed process records and the complete prior-rung chain. The old receipt is not replaced by accepting current sources. A newly prepared build remains `build-recorded-pending-independent-review` until its concrete compiler/header/library/executable record is reviewed. The current phase-process generation and resource limits must be carried through a current plan. These are concrete remaining prerequisites, not grounds to bypass the original record.
