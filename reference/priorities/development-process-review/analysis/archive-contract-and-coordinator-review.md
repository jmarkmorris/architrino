## Conclusions

The remaining coordinator pin selects a substantially different interface, not an intermediate edit or a terminology-only revision. Its exact source has been recovered. Advancing that pin alone would select a producer whose completion record the existing independently frozen verifier rejects. The required repair is an explicit migration of the live parent-batch completion contract, with the old evidence reader preserved at its historical scope.

The historical archive problem combines three separate questions: whether retained scientific evidence has the expected bytes, whether its recorded execution provenance is trustworthy, and whether every executable from the original environment remains available for inspection or replay. The current parent source pool treats the last question as a prerequisite for the first two. That is an actual implementation requirement, not an intrinsic property of a cryptographic hash. Changing it needs an explicit contract and honest claim boundaries, not an exception that turns a failed full-identity check into success.

The recommended direction is to preserve historical identities and evidence, use current runtime identities for new work, and report historical runtime availability separately. Exact scientific inputs and independent validation remain mandatory. Unavailable old host tools must remain visible as an archival limitation; they must not be silently replaced with current tools or counted as verified originals.

| Historical utility | Recorded role | What its original bytes would help audit | What possessing those bytes cannot establish now |
| --- | --- | --- | --- |
| `git` | Required runtime; the preparation source invokes `check-ignore` to confirm its output lane is ignored | The implementation of that filesystem-policy check | That the old command actually ran with the recorded arguments and outcome |

These are meaningful operational dependencies. They are not the mathematical evaluator in the inspected paths. ## Proposed historical archive contract

The following is a proposal for operator review, not an accepted replacement for the existing strict contract.

1. **Keep original identity immutable.** An original logical path, its digest, and its byte count come from a separately pinned historical receipt or acceptance record. A later file at that path is a different generation, even after a mechanical edit. A physical archive path has its own filesystem identity; it never inherits the original inode or timestamps.
2. **Separate scientific bytes, current execution bytes, and historical environment metadata.** Historical data, mathematical/reference sources needed to interpret it, and applicable proof documents remain exact byte requirements. Current executables, interpreter, and host observers are bound for the new run. The historical environment list remains intact as provenance, with explicit availability for each original binary.
3. **Use one nonexecuting archive resolver.** Resolve an explicitly admitted original tuple to one exact physical archive tuple. Preserve same-descriptor reads, byte limits, unique membership, rejection of symlinks/hardlink aliases where the current contract requires them, and final rechecks. Include actual archive files in the current physical capture union, while comparisons against historical receipts use original logical identities. Do not feed original and current generations at the same logical path into a single path-keyed map and hope one wins.
4. **No executable authority from an archive.** The resolver supplies bytes for inspection. It must not import, evaluate, spawn, or select historical code as the current implementation. In particular, preserving the original entry for extracting its pins does not authorize running that entry.
5. **Preserve closure evidence as closure evidence.** Verify the original record's identity, the relevant independently recorded closure/acceptance observations, and the precise claim they support. A present-day hash match cannot prove a past exit, memory observation, or deadline. Missing originals limit retrospective implementation audit; they do not manufacture or erase the recorded observation.
6. **Keep the strongest claim unavailable until its requirements are met.** A result may distinguish verified retained scientific bytes and verified recorded provenance from incomplete historical environment availability. It must not emit the old full-source-authenticated claim, reuse its success label, or silently pass the old check when original host-tool bytes are unavailable. Consumers must explicitly choose the narrower contract if approved.
7. **Do not rewrite old evidence to fit the new interface.** Introduce the new contract at the live consumer boundary with explicit versioning. Preserve an original-identity reader for old records. Historical comparison predicates must use the values actually recorded by their old plans, not the current verifier's own digest or its current declaration digest.

A decisive control set for implementation is: reject a wrong or missing scientific archive, a forged original tuple, a same-path current-generation substitution, an unused route, conflicting duplicate identities, a changed physical file, an executable archive request, and any promotion from incomplete host availability to full original-source authentication. Positive controls must simultaneously exercise distinct current and original versions of the same logical source. The independently authored checker should receive its own literal contract controls before the producer adopts the new contract; changing both to agree is not independent validation of the policy.

### The decision for the operator

**Recommended:** permit a separately named historical-evidence verification result that requires exact scientific artifacts and independently anchored provenance, while reporting unavailable historical host executables explicitly. Preserve the strict full-original-environment result as unavailable until all original bytes are recovered. This allows useful evidence verification without making a promise of exact environment recovery that the available material cannot support.

The alternative is to retain complete original-environment byte availability as a prerequisite for every use of the old evidence. That is coherent, but it keeps this lane blocked until the three utility versions are recovered and the archive route is implemented. A new run under the current environment could generate new evidence; it would not repair or recreate the old run's original identity. No numerical rerun is recommended as an immediate substitute for this decision.

## Coordinator repair order

The recommended repair is a forward migration of the live parent-batch caller and its independent closure observation to the canonical coordinator's explicit completion contract. Preserve the old reader for old records, rather than executing a second old coordinator or reverting the current implementation. This is not a proposal to accept pending closure.

1. Specify the exact external observation required after conditional completion: the original invocation's exit status and elapsed-time boundary; guard, worker, process-group, and lock closure; retained source/output identities; and the relationship of the final observation to the pending operation record. Identify which observations are available in the current wrapper and which need a dedicated observer. The generic ownership wrapper's group-closed field alone is insufficient.
2. Author and independently validate that observation/checking boundary with literal fixtures that reject pending-only, missing guard/lock evidence, stale identities, late exit, source/output substitution, and incomplete logs. Keep mathematical artifacts unchanged.
3. Adapt the current parent batch to that reviewed boundary, then update its current coordinator selection and regenerate only newly authorized launch plans. Do not modify old invocation records or old evidence pins.
4. Run bounded synthetic success and failure cases with actual external closure before permitting a scientific batch. Keep the scientific launch and its acceptance separate.

This is the next implementation proposal, not a completed migration. The recovered source and incompatible output requirements are sufficient to reject blind repinning now. A demonstration that the existing independent checker accepts the unmodified current output with independently complete closure would overturn this incompatibility conclusion; comparing module hashes or passing metadata-only controls would not.
