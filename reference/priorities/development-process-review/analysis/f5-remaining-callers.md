# F5 original-input caller execution

The current-input problem has two distinct consumers. The display uses the current version-three assembly schema and canonical member names. The frozen F5 preparation, prefix, ledger and Python conformance instruments require the original version-two scientific input bytes at their declared logical names. Replacing the current display file with those originals would break the current schema, while advancing the frozen input digests would change the question the independent instruments check.

## Explicit execution root

[The input-tree materializer](../../../../scripts/eom/prepare-f5-original-input-tree.mjs) provides an explicit production execution root. It copies the current consumer/reference source files without alteration and places the five authenticated original data objects under their required logical names inside ignored storage. The existing production CLIs then execute normally from that root; no test-only validator entrypoint, injected reader, schema projection, reference-code modification or historical digest substitution supplies their authority. This is a filesystem transport, not a second implementation of any F5 calculation.

The materializer checks each original against its independently fixed SHA-256 identity and declared byte count. It rejects duplicate, missing or altered route identities, noncanonical route names, symlinked files/parents, nonregular files and an existing output root. File opening is nonblocking so a FIFO is rejected by `fstat` instead of hanging before that check. It verifies source census and captured bytes again before writing its last materialization record. `--check-root` compares the complete record and copied files with the current source census and exact originals. Partial directories without that record are unusable. The record explicitly has `accepted: false` and `scientificAcceptance: false`.

These checks establish path-based byte consistency at the measured boundaries. They are not atomic runtime authentication and do not bind an interpreter, dynamic loader or compiler execution. A source change in the origin invalidates the current check and requires a fresh root. Each consumer retains its own identity, build, proof and output-acceptance obligations. The copied source profile covers the named F5 preparation, prefix, ledger, interpolation and two Python conformance interfaces; it is not a claim of complete repository dependency capture.

From the repository root, the production interpolation path is:

```bash
node scripts/eom/prepare-f5-original-input-tree.mjs --out-root .local-data/f5-original-input-trees/NEW
node scripts/eom/prepare-f5-original-input-tree.mjs --check-root .local-data/f5-original-input-trees/NEW
node scripts/dev/owned-compute-supervisor.mjs run --owner-task "$CODEX_SESSION_ID" --deadline-seconds 60 --cwd .local-data/f5-original-input-trees/NEW -- node scripts/eom/derive-f5-independent-interpolation-enclosure.mjs --out interpolation.json
node scripts/eom/prepare-f5-original-input-tree.mjs --check-root .local-data/f5-original-input-trees/NEW
```

The same `--cwd` root supports the unchanged `prepare-f5-enclosed-root.mjs`, `verify-f5-enclosed-root-prefix.mjs` and `reduce-f5-enclosed-root-ledger.mjs` CLIs with their documented arguments. Pass that execution root as `--repo-root` where requested, and supply the shared venv as an absolute `AAA_VENV` for preparation; the root's adjacent directory is not the shared venv. A full preparation requires its own fresh build, complete nominal proof and independent build/API-domain review. The prefix and final reducer require actual accepted history and rung inputs. Materialization supplies none of those results.
