Status: proposed plan for operator discussion, 2026-09-07. Analysis and evidence capture are authorized. Implementation, broad test execution, publication, credential changes, and workspace migration are not activated by this document. The [operator concerns](operator-concerns.md) define scope; the [five reports and post-report statements](../README.md#evidence-inventory) remain unchanged source evidence.

## Assessment

The evidence supports several interacting problems: changes to files whose exact bytes were recorded elsewhere; incomplete test coverage in publication checks; test environments that could not execute the intended workloads; a process-termination problem; and access troubleshooting that repeatedly confused tool availability, authentication, and permission to write. Treating these as one hash problem would encourage the wrong repair. Treating them all as environmental would leave actual assertion failures unexplained.

The priority is to restore trustworthy validation and review the changes most capable of weakening it. A complete redesign of the hash system, a different merge method, or moving projects should follow that evidence. None is established as the cause or cure of the incident. The [evidence assessment](cross-report-findings.md) distinguishes independently inspected facts, reporter claims, and outstanding investigations.

The strongest early repair candidate is process supervision: tests cannot give a dependable result if the processes they launch do not terminate. Equally urgent is checking that the pin repairs and changed test expectations did not redefine success without justification. These two investigations can proceed independently after their relevant evidence is preserved; they do not need Claude's GitHub access or a parent-folder project.

## First bounded investigation

Start with the process-termination family and the bootstrap test's changed cleanup claim. Read the complete lifecycle contract and code before choosing a remedy. The current source suggests a possible dependency between a runner and its watchdog process, but this is a hypothesis, not a reproduced diagnosis. The investigation should distinguish unfinished work, an open communication channel, process-group enumeration, and cleanup waiting on an event that cannot occur.

Use one synthetic test with a separately controlled overall deadline and cleanup procedure. Record the environment, start and completion events, process identities and parent/group relationships, and which handles or processes survive. Compare Node 22 and Node 26 on the same Mac when both can be run under the intended prerequisites; this isolates a runtime variable but cannot by itself explain Linux behavior. A same-host version comparison is informative whether the results agree or differ. Do not install a runtime or start another full sweep as part of this planning pass.

Acceptance must include successful completion, interruption before ownership authentication, interruption after authentication, and a failed child. An independent process census must establish that owned processes are gone. A receipt that says `processesClosed` is evidence from the implementation under test, not an independent census. Cleanup must retain the protection against signalling an unrelated or unauthenticated process. Any proposed change must be checked across other launchers sharing the mechanism, with meaningful controls rather than pin equality alone.

The stopping point for an investigation batch is one supported cause, one disproved hypothesis, or one concrete missing observation. Repeating the same failed command without a changed input, environment, or discriminating observation is not progress. Record useful results before changing approach. This limits the chance of another open-ended session without inventing arbitrary claims about how many minutes a repair will take.

## Repair audit and failure-family order

Audit the bootstrap expectation change first because it affects the evidence for process cleanup. Next examine the launcher/dispatcher pin refresh against its prior launch-readiness claim, recovered uncommitted baselines, and changes to evidence files during the earlier rename campaign. Enumerate actual commit diffs for the reported repair commits rather than attributing files from subjects or shared author metadata. The audit should separate mechanical changes, behavior changes, mathematical changes, and changes to what tests accept. It is not necessary to prove all mathematics again for a spelling-only change, but a spelling-only diff does not independently validate the mathematics.

The supported-host inventory should group by cause rather than by the order a test runner printed failures:

1. Process supervision and cleanup, including owned-compute behavior under the actual host's filesystem permissions.
2. Configuration/schema migration: current v3 inputs versus older fixtures and required assembly identities. Preserve historical fixtures; determine whether a current test needs a new fixture or is deliberately reproducing an older claim. Do not add general compatibility behavior just to silence errors.
3. Reviewed-source and scientific-dependency changes: EOM source, methodology coverage, the Master Equation certificate dependency, and bounded-operation controls. Their owners must assess the relevant obligation before pins move.
4. Product/runtime behavior: Borg loading and geometry, Archie contract drift, database API compatibility, and renderer assets. Split missing generated prerequisites from incorrect outputs; a renderer regeneration request is a separate authorized operation.
5. Residual failures and deliberately invalid fixtures. An intentionally missing fixture can be part of a passing negative test; a regex finding the missing path alone is not a defect.

This order is proposed by consequence and shared dependencies. A narrowly verified, independent low-risk repair need not wait behind a longer scientific decision. Conversely, a failure affecting a scientific claim moves ahead of convenience defects even if its owning lane is otherwise deferred. Record that prioritization explicitly with the owner rather than silently reactivating the whole lane.

For each repaired family, require the relevant failing case to pass and a meaningful negative or independent control to continue rejecting the wrong behavior. Re-run the family after the change, then broaden only as needed for affected dependencies. A temporarily excluded test needs its reason, owner, and revisit condition visible. It cannot count as a repaired test. Final recovery should have no unexplained failures in the supported test inventory; any retired test needs a documented obsolete obligation or adequate replacement.

## Testing arrangement to decide

The proposed design is based on test purpose and execution requirements first, duration second. Fast behavioral checks and inexpensive integrity checks can provide early feedback. Process and integration tests need a real, supported environment and reliable termination. Historical reproduction checks may need archived inputs rather than the current source tree. Expensive scientific campaigns need explicit execution and evidence controls. Putting all of these into a single duration bucket obscures their differences.

A publication check should state its scope accurately. The current runner can skip the sweep and end with “all checks passed”; it can also report non-gating failures and still exit successfully. Those behaviors are visible in the source and technically consistent with its current contract, but the overall wording can imply more health than was measured. The proposed correction is to distinguish required-check success, unresolved diagnostic failures, and unexecuted coverage in the final result. Similarly, “the first is the likeliest root” is not justified merely by the order of independent checks. Preserve useful failure order without presenting it as causal analysis.

Decide which relevant suites block a PR, which run in a separate supported job, and which are explicit research runs. Introduce a broad CI suite only after its prerequisites, bounded behavior, and reporting are demonstrated on the intended runner. Making a job nonblocking does not keep it from hanging or consuming resources. A green run once is necessary evidence for promotion but is insufficient by itself to show reliable termination or meaningful coverage. The current two workflows duplicate the content gate; evaluate whether that duplication provides a needed guarantee before changing it.

## Coordination and merge choices

The operator's historical account is publication through Codex while Claude might still have been writing, not simultaneous development by both agents. That distinction is preserved. A Git commit is a snapshot of selected file contents; it does not know whether an agent has finished a multi-file task. The current receipt captures before/after state, which can detect some changes during validation, but it is not a writer-completion protocol. The review should also check whether partially staged files can cause tests of the working files to differ from the contents actually committed. No such race has been demonstrated for this incident.

A modest interim arrangement is preferable to building a coordination service immediately: identify the task owner, agree shared-file handoffs, and have the designated publisher obtain a stable completed set before validation and commit. Read-only analysis can continue; writes to the publication set need coordination. Direct Claude/Codex messaging is an optional future capability to verify, not a dependency.

Git worktrees provide separate working directories attached to one repository and allow different branches to be checked out concurrently. They separate edits but still require integration. The trial to consider later should test the operator's actual needs: seeing changes, shared venv and ignored assets, access to MyLists, combining work, and returning a completed task to publication. The prior unsatisfactory experience is not evidence of operator error. [Git worktree documentation](https://git-scm.com/docs/git-worktree).

Squash merging combines a PR's commits into one main-branch commit. GitHub documents both its simpler main history and its loss of individual commit history there. A squash does not itself change file bytes just because it changes commit identity. The report's recovered uncommitted blobs are a reason to investigate how baselines were preserved; they do not establish that squash merging caused the original mismatch. Decide whether the repository needs preserved intermediate history, smaller PRs, or durable evidence snapshots before changing merge policy. [GitHub merge-method documentation](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/about-merge-methods-on-github).

For Claude access, identify the actual channel first: built-in repository integration, custom MCP tools, local Git, or a local CLI. The reports show a successful profile read and failed PR writes; they do not identify the exact permission configuration responsible. Inspect that configuration without exposing secrets, then use a minimal explicitly authorized write that exercises the required capability. Retry only after a relevant change. Do not infer capability from a connected badge, a write-named tool, or a successful read. The operator's prohibition on using GitHub through the browser remains part of the recorded access history.

For the parent project, obtain the existing Claude description before proposing a replacement. Verify current Codex project and task-migration behavior with local app information and official documentation. Keep repository-specific instructions identifiable even if the project root is their parent. A shared parent directory is not a merger of the two Git repositories. If tasks cannot move directly, prepare a checked continuation handoff and trial one task before changing all of them. These capability questions remain open; this plan does not assert that the app already supports the requested arrangement.
