## Minimal reader and receipt contract

Use `jsonld` for standard JSON-LD processing, `n3` for an in-memory RDF/JS store, and `@comunica/query-sparql-rdfjs` for local SPARQL queries. Keep the approved local context and strict application schema. Derive the impact view from the one authoritative relationship set and query it with fixed, reviewed queries. Preserve mathematical dependencies, verification targets, check coverage and run provenance as distinct predicates/roles. Graph traversal establishes declared reachability only. The library comparison and implementation boundary below supersede the earlier custom fixed-context engine proposal.

Reject duplicate JSON keys, unknown fields/types/predicates, remote contexts, unsafe or escaping paths/symlinks, duplicate identities/edges, dangling or stale versions and reused revision IDs. Enforce endpoint types for all five predicates, not just the subset checked by the pilot. Commands come from a fixed catalog in code, never records. Bound input sizes and traverse cycles without treating a cycle as a proof. A source or edge difference always remains review-required; removed check obligations persist until explicit reviewed retirement.

For the four equation objects, use `parseCorpusDisplayEquations` from the existing generator to resolve the occurrence identity and line span, then hash the original byte lines. Do not use its normalized TeX as the binding, or its string offsets as UTF-8 byte offsets: the parser splits CRLF and trims formula text. Other bindings use unique literal spans or whole files. Replace snapshot-specific line selectors in the new live map with explicit unique start/end anchors where feasible; reject ambiguous or missing anchors. Preserve the candidate's historical selectors and bytes. Every unselected whole-file change remains visible and conservatively selects the chain's two checks.

Separate stable authored knowledge records from emitted activity/output records. Do not embed the pilot's scratch environment or run as the current live producer. Capture each new scalar output verbatim, execute the unchanged test, compare the unique displayed maximum with that run's output, and write a separate immutable evidence bundle. Record exact input, instrument, output and environment identities. The historical prose measurement remains a comparison target; never relabel the new run as its historical producer.

**Receipt insertion point:** add the chain command to `VALIDATION_COMMANDS` in `pr-validation-receipt.mjs`, following Content Integrity. The command-list hash automatically invalidates old receipts. Extend receipt write/verify with a chain-evidence digest and verified input identity, because files under ignored `.local-data` are outside the current untracked-content fingerprint. `verifyValidationReceipt` must reject a missing/altered bundle or changed baseline descriptor, not merely trust a stored success flag. Capture the externally selected baseline descriptor digest in state before checks and compare it afterwards, so changing the descriptor during validation cannot preserve a receipt. Update tests around `runValidationAndWriteReceipt` and `compareValidationStates` accordingly.

The [Content Integrity workflow](../../../../.github/workflows/content-integrity.yml) runs Content Integrity directly under Node 22; it does not run `pr-validation-receipt.mjs`. The proposed first implementation is the local receipt integration, tested on Node 22-compatible APIs, plus fixture CI tests. It does not claim that the chain becomes an independent required remote check. Changing CI/branch-required checks is outside this bounded implementation decision.

### Language-neutral stack assessment

**Operator preference:** no strong language preference. Python was suggested for its established libraries; comparable JavaScript libraries are acceptable. Selection should prioritize maintainability, correct standard interpretation, useful graph capabilities and existing integration. Avoiding one dependency installation is not an adequate reason to reimplement a standard graph layer.

| Option | Documented capabilities | Project tradeoff and disposition |
| --- | --- | --- |
| Python with RDFLib | Integrated JSON-LD parsing/serialization, graph and dataset interfaces, memory/persistent stores and SPARQL 1.1 query/update. [RDFLib documentation](https://rdflib.readthedocs.io/en/stable/) | Strong alternative with the least translation from the measured pilot and one principal graph package. A Node CLI can invoke it; the language boundary is manageable. Requires supported Python/dependency provisioning and receipt identity on each validation host. The local macOS venv does not itself provide the existing Linux CI environment. |
| Node with `jsonld`, `n3`, and `@comunica/query-sparql-rdfjs` | `jsonld` expands JSON-LD and converts to RDF; N3 provides RDF/JS storage; Comunica explicitly supports querying an N3 store and offers a smaller RDF/JS-only query engine. [jsonld.js](https://github.com/digitalbazaar/jsonld.js), [N3.js](https://github.com/rdfjs/N3.js), [Comunica integration](https://comunica.dev/docs/query/advanced/rdfjs_querying/) | **Recommended.** Standard processing and graph queries without a custom standards engine, in the same runtime as the equation parser, scientific checks, tests and receipt. Costs are three direct packages, their transitive dependency/upgrade surface, and explicit RDF conversion/store boundaries. Those costs are real; no dependency-size or runtime advantage was measured. |
| Custom fixed-context Node graph reader | Could interpret the deliberately small candidate format and hand-code reachability. | Reject as the production graph layer. It makes the project maintain a special interpretation and query implementation when established alternatives exist. Keep only application-specific validation/adaptation. |

The recommendation is an integration judgment, not a finding that Node libraries are scientifically more correct than RDFLib. RDFLib remains a credible fallback if the selected Node versions fail the required compatibility or offline acceptance cases. Do not maintain both as production readers. The existing Python pilot remains historical evidence, and can serve as a separately retained comparison on fixed graph fixtures; agreement between ports does not establish semantic completeness.

**Concrete pipeline:** validate raw records and reject duplicate JSON keys before information is lost; process the allowlisted context with `jsonld` in safe mode; convert with its documented N-Quads output; load those quads with N3; query the store through the RDF/JS-only Comunica engine. `jsonld` documents a configurable document loader and safe mode for lossy-processing errors. Supply a loader that rejects every undeclared URL, with no default network fallback. Safe mode is not a sandbox or an application-schema validator. Use only fixed local queries without `SERVICE`, remote sources or updates. [JSON-LD processing and loader documentation](https://github.com/digitalbazaar/jsonld.js#custom-document-loader), [Comunica RDF/JS sources](https://comunica.dev/docs/query/advanced/rdfjs_querying/).

Library-owned responsibilities are JSON-LD expansion/context interpretation, RDF terms and datasets, serialization, and SPARQL evaluation. Project-owned responsibilities remain source selectors and exact-byte hashing; immutable object/edge revisions; meaning and allowed endpoints of `dependsOn`, `verifies`, `checks`, `usesInput` and `generatedBy`; old/new obligation retention; trusted baseline selection; scientific command execution; result accuracy and receipt consumption. Standard processing cannot discover a scientifically omitted edge or approve a change. Materialize direct impact triples as a derived view with the original relationship records retained, never as a second editable map.

Keep old and new snapshot stores distinct, or use explicitly named graphs with correctly scoped blank nodes. Check the union of their relevant impact paths according to the existing obligation rule; do not accidentally equate blank-node labels from separately parsed documents. RDF-equivalent serializations can differ in exact bytes, so semantic graph comparison must never replace the current byte-change review boundary. Dataset canonicalization is not needed to authenticate the original input bytes.

**Provisioning and version contract:** the local shared Python ran as 3.13.2 and lacked RDFLib in the prior live probe; that absence is a provisioning fact, not an argument against Python. The Node packages are also absent from the inspected `package.json`/lockfile. Add compatible, explicitly pinned direct versions and the resolved lockfile only during authorized implementation, using the existing Node 22 CI target and local Node runtime. Do not treat latest default-branch documentation as a tested version selection. Review licenses/dependency audit and run the small pipeline/graph fixtures before integration. Record lockfile digest, actual resolved package versions, Node/platform and adapter identity in the evidence; reject receipt reuse when these inputs change. Provision validation hosts with the lockfile through `npm ci`; do not auto-install from a Git hook. No package was installed by this assessment.

RDFLib also warns that parsing contexts and executing queries may access network or file resources; choosing either language requires explicit offline restrictions. [RDFLib security guidance](https://rdflib.readthedocs.io/en/stable/security_considerations/). No remote-data feature, new approval service, general reasoning engine or wider scientific pilot is needed here.
