# Prevention proposals against the B and publication workflows

Review date: September 12, 2026. The operator selected review of the [RCA's seven prevention proposals](../../analysis/option-a-validation-root-cause-analysis.md#prevention-proposals-ranked-by-the-demonstrated-risk), beginning with source-role preservation and final-composition validation. This companion review preserves the historical RCA and existing workflow subjects. It changes no production implementation, selected expectation, policy, generated output or publication state.

The principal recommendation is to retain B's existing source-role and transition controls, verify their transfer through each remaining real consumer, and strengthen the existing publication receipt's treatment of dependencies outside the index. The latter has a new bounded counterexample: a stable unstaged dependency can make a working-file consumer pass while the corresponding indexed candidate contains incompatible inputs. Existing partial-staging rejection does not cover that case.

## What the two primary proposals require

A source role states why particular bytes matter. Historical evidence records what supported an earlier result; a current operational selection identifies the implementation permitted for a new invocation; an independent reference or scientific contract carries its own applicability and acceptance obligations. Moving an identity into a B record must preserve that purpose. A matching digest alone cannot decide whether a historical record should change or whether a revised reference remains valid.

Final composition means the sources, declarations, selected records, workers and required checks actually used together. There are two relevant boundaries: the composition admitted for execution and the composition entering a commit. A checker can correctly validate a declared source graph while missing an undeclared consumer, and a receipt can correctly fingerprint working files that differ from the index's eventual publication contents. Both distinctions matter to the original mixed-generation defects.

## Source-role preservation: substantially implemented at the inspected B boundary

Measured by direct reads of the [admission contract](../../contracts/option-b-current-source-admission.md), [B-to-B contract](../../contracts/option-b-current-source-transition.md), [transition implementation](../../../../../scripts/equation-mapping/current-source-transition.mjs) and [five-profile checker](../../../../../scripts/equation-mapping/check-current-source-maps.mjs), the original-five boundary already provides the following protections:

| Required protection | Existing enforcement | Limit |
| --- | --- | --- |
| Select a current successor outside the candidate | Caller supplies the accepted-checkpoint and reviewed-transition paths and digests; edited records cannot retain the original selections | The code authenticates selected bytes, not the identity or competence of the human reviewer |
| Preserve historical evidence | The checkpoint retains historical/scientific evidence categories and values; the historical transfer proof is captured as data; admission tests compare retained entry values with those records | It does not rerun historical scientific evidence or infer its applicability to a new result |
| Deny source refresh by default | An exact path/role grant must already exist in the externally selected predecessor; candidate transitions cannot add grants | A separately accepted checkpoint or policy extension still needs substantive review |
| Prevent a broad role label from authorizing a scientific edit | Even `current-source` rows require explicit eligibility; scientific/reference/control/resource-plan/reader roles remain protected | A complete obligation inventory is still needed beyond the declared profiles |
| Preserve graph and revision meaning | Exact derived changes must equal the reviewed changes; role/path/scope/coverage/ancestry rewrites reject; changed records require new revisions and consistent endpoints | The graph represents declared dependencies; this reader is not a complete static or dynamic dependency-discovery instrument |

Measured by the [83-control focused run](prevention-focused-tests.log), the current transition suite rejects attempted successors for the actual acceleration reference proof and normalized-member predeclaration even though their inherited labels say `current-source`. It first accepts copied unchanged inputs, then constructs graph-valid revisions and observes rejection at the missing-eligibility condition. This directly supports keeping the predecessor-grant rule instead of relying on a label-cleanup campaign.

The same run exercises the actual five admission entries and captured workers. It verifies retained historical values, source census, map/source inclusion in plan bindings, conflict rejection, failed-initialization cleanup, changed/missing reader or source rejection, wrong-profile maps, and launch/stage rejection before a missing scientific plan is consumed. The saved full-profile pilot plan is explicitly tested as historical evidence despite its repository location. These are bounded source-admission controls; they do not constitute scientific workload execution.

**Recommendation:** accept proposal 1 as an existing control to preserve and extend through the live [Option B continuation](../../analysis/option-b-redux-handoff.md) and [queue](../../work-queue.md). For each remaining family, identify the old obligation, its B representation, the actual enforcing consumer, the predecessor selection, permitted changes and preserved rejection behavior before retiring A's implementation. Use the existing disposition and reconciliation owners. No additional blanket pin sweep, blanket refresh authority or duplicate acceptance system is justified by this review.

Falsifier: an ungranted source change or protected-role change accepted under unchanged external selections by `inspectCurrentSources`, or a migrated real consumer bypassing its retained evidence/source checks, overturns the corresponding bounded preservation claim. Full-B coverage remains unestablished by this review.

## Final composition: existing execution controls and a publication gap

Measured by reading `captureSet`, `inspectCurrentSources`, the root-cover entry's `initializeSourceBindings`, `planBindings` and `checkBindings`, B authenticates selected regular files, rejects conflicting shared identities, combines map and retained plan bindings, and rechecks captured originals before reporting source consistency. The focused suite passes stale-source and original same-byte replacement controls. These mechanisms address intermediate-generation selection and subsequent source changes when the dependency is declared and the real entry is used.

The original RCA's two document mismatches and intermediate preparation case should remain explicit review examples: a historical reference must keep its original identity, while an admitted current successor must select its final bytes and reach every affected consumer. Existing stale-source, retained-evidence, conflict and worker-recheck controls already cover much of this behavior. Add only the missing cross-route case for a family being migrated; do not reproduce every old numerical campaign merely to test selection.

Measured by direct reads of the [publication procedure](../../../../op/git/pr-lifecycle.md#shared-checkout-coordination), [receipt implementation](../../../../../scripts/pr-validation-receipt.mjs) and hooks, publication already requires writer readiness, paused development, final staging, before/after state equality and renewed checks after candidate changes. The receipt fingerprints index entries, the unstaged/untracked overlay, base, branch, command contract and runtime platform. `assertStagedFilesMatchWorktree` additionally rejects a path appearing in both the staged and unstaged change sets. The focused run passes both partial-staging rejection controls and state-change invalidation.

The remaining limitation is distinct from those repaired cases. The [isolated boundary diagnostic](prevention-receipt-boundaries.mjs.source) uses the actual receipt API and a separately stated two-file consumer: it reads `requirement.txt` and `dependency.txt` and requires equal contents. Before the diagnostic target, the coherent indexed/working positive passes, and the known partially staged negative rejects before running its consumer; those controls are recorded first in the [execution log](prevention-receipt-boundaries.log).

| Fixture state | Working files used by the consumer | Indexed files that would enter a commit | Observed result |
| --- | --- | --- | --- |
| Known coherent positive | requirement `old`; dependency `old` | requirement `old`; dependency `old` | Consumer passes; receipt verifies |
| Known partially staged negative | requirement differs from its staged version | Same path has staged and unstaged changes | Receipt runner rejects before invoking the consumer |
| Stable unstaged dependency | requirement `new`; dependency `new` | requirement `new`; dependency `old` | Working consumer passes and receipt verifies; indexed values violate the consumer's independent equality requirement |

This is a **measured receipt-boundary limitation**, established by the actual `runValidationAndWriteReceipt` and `verifyValidationReceipt` functions with an injected synthetic consumer. It is not a full Content Integrity pass, proof of a production PR escaping CI, or retrospective attribution of the original incident. No production gate or scientific consumer was replaced on disk. The diagnostic's temporary repositories are ordinary isolated fixtures, not linked worktrees, and were removed by its cleanup.

The reason is visible in `assertStagedFilesMatchWorktree`: it checks the intersection of changed staged paths and changed working paths. A dependency modified only in the working files is outside that intersection. Fingerprinting that stable overlay accurately records the tested state, but does not prove the index would reproduce the result. The procedure's allowance for unrelated ambient changes therefore needs a demonstrated dependency boundary; a file cannot count as unrelated if a required consumer uses its uncommitted contents. Writer inactivity and state stability alone do not establish that boundary.

The [GitHub workflow](../../../../../.github/workflows/content-integrity.yml) and publication procedure supply complementary fresh-checkout checks. Their protection remains narrower than equivalence with every local result: the explicit GitHub profile assigns two shared-Mac-venv admission tests to mandatory local validation. A portable CI pass cannot supply evidence for those local-only tests.

**Recommendation:** extend the existing receipt and publication workflow with one requirement that validation inputs match the indexed candidate: every repository source input used by the required local validation must agree with the indexed candidate. Preserve unrelated ambient work, but reject receipt creation/reuse when an uncommitted dependency supports a claimed candidate result. Start implementation with the demonstrated two-file negative and a coherent positive in the existing receipt suite, then connect enforcement to the actual validation inputs. An inventory limited to changed filenames or a stable overlay is insufficient. If a proposed enforcement design cannot establish input completeness, it must not claim candidate equivalence. This is a proposed extension; the review does not select a new workspace arrangement or implement a new validation system.

Falsifier: if the recorded diagnostic stops producing a valid receipt for the incompatible indexed pair, or an existing mandatory local candidate check is shown to exclude that case before publication, revise this gap assessment. A future repair should reject the incompatible pair while retaining the coherent positive and existing supported unrelated-work behavior.

For proposal 3, the additional diagnostic first proves that a clean-environment Git child resolves its own fixture. It then gives the actual validation runner all eight conflicting repository-scoped Git variables pointing at a separate temporary sentinel. At each of its five spawn boundaries, the diagnostic verifies those variables are absent and executes a real Git child that resolves the intended fixture. The sentinel configuration remains byte-identical. Validator workloads are substituted by this diagnostic child; this measures environment forwarding, not a full inherited-hook gate run. A surviving variable or a child selecting the sentinel would falsify the result. The existing receipt test source was read in full; it sanitizes fixture commands but does not contain this deliberately poisoned-parent regression.
